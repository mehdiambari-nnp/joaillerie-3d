# Journal des décisions
Décisions de conception, par ordre chronologique (les premières ont été prises en autonomie : consigne « ne me pose plus de questions »). Les sections marquées *(historique)* décrivent un état **remplacé** : le texte est gardé pour expliquer le pourquoi. État courant : `README.md` et `docs/FIREBASE.md`.
- **Stack** : Vite + JS vanilla, three.js épinglé 0.183.2 (compatibilité model-viewer), versions exactes.
- **Repère** : mm, doigt = +Z, dessus = +Y, origine = centre du doigt (trou mesuré par rayons radiaux + cercle de Kåsa).
- **Zones** = regroupements ; **affectations par pièce** ; sélection par zone (défaut) ou par pièce.
- **Doublons** (Objet_19/20/21 superposés dans la maquette) supprimés à l'import, signalés dans le rapport.
- **Pierres** : normales plates (facettes), matériau physique (transmission, ior ≤ 2,333, dispersion).
- **iOS** : pas de WebXR → AR = Quick Look (USDZ) ; essayage = caméra + MediaPipe + three.js dans la page ; HTTPS requis pour la caméra.
- **Fichier** : détection du format par l'en-tête (iOS ignore `.fbx`), pas de `accept`.
- **Partage** : lien `#c=` (lz-string), sans serveur ; projet GLB avec config dans `extras`.
- **Essayage** : pose depuis les landmarks monde ; occluder cylindrique ; vidéo en fond de scène pour réfraction des pierres ; filtre One Euro ; LOD 25 %.
- **Diamètre intérieur de la maquette** : 19,49 mm (taille FR 61) — l'estimation initiale du brief (18 mm) était fausse, corrigée.
- **Bug corrigé** : import GLB asynchrone (`parseAsync`) ; mise en page iPhone élargie par les rangées défilantes.

## Itération 2 : qualité graphique + calage de l'essayage
- **Environnements HDRI** (Poly Haven, CC0 : venice-sunset, quarry, overpass, spruit-sunrise, dans `public/hdr/`) en plus des 3 studios procéduraux ; rotation, exposition, fond 360° visible (option « Environnement ») avec flou réglable. Chargement asynchrone + cache, repli sur fond clair en cas d'échec.
- **Fond toujours défini** (dégradé dithéré ou env) : les pierres en transmission réfractent `scene.background`, un fond transparent les rendait pâles.
- **Pierres incolores** : léger « sparkle » (metalness 0,15, envMapIntensity 2,2), épaisseur 6 mm. Haute résolution (DPR jusqu'à 3) après 400 ms d'inactivité.
- **Essayage : cause du mauvais placement** : les world landmarks MediaPipe ne sont pas métriques (paume ≈ 0,73×, doigts compressés). Nouvelle méthode : échelle = taille de la paume dans l'image / moyennes anthropométriques (médiane de 5 segments), relief = world landmarks normalisés à l'échelle image, dessus de la bague toujours vers la caméra (l'étiquette gauche/droite ne distingue pas dos/paume). Validé sur 2 photos réelles (`tests/fixtures/`, `docs/tryon-calibration/`).

## Itération 3 : retours client (matériaux, plein écran, mode client)
- **Plein écran** : la grille de l'app gardait une ligne vide quand la barre du haut était masquée (la vue 3D ne s'agrandissait pas) et il n'y avait aucun moyen de sortir sur iPhone (pas d'Échap). Désormais : vue 3D seule + bouton « Quitter le plein écran » toujours visible.
- **Métaux** : or jaune, rose, rouge, gris, platine (plus blanc que l'or gris), sans titrage. Finitions : poli, satiné, brossé, martelé. « Teinte libre » (couleur + code + teinte/intensité/clarté).
- **Pierres** : diamant seul pour l'incolore (moissanite/CZ identiques à l'écran, supprimés) ; ensuite des pastilles de COULEUR groupées par famille (rouges, roses, orange/jaune, verts, bleu-vert, bleus, violets, noir/nacre), sans noms d'espèces ; teinte libre. La couleur choisie devient la couleur d'atténuation de la pierre (Beer-Lambert).
- **Pantone** : la bibliothèque Pantone est propriétaire (licence payante) → remplacée par un sélecteur libre (code hex, teinte/intensité/clarté). Un import de nuancier (RAL/Pantone fourni par le client) est possible plus tard.
- **Modes** : Client (épuré : vue 3D, rotation, plein écran, AR, essayage, photo ; aucune sélection ni réglage), Joaillier (configuration), Atelier (zones/règles). Le « lien client » (`k:1` dans le lien) verrouille l'interface en mode client.
- **Compatibilité** : anciens identifiants (gold18, sapphire…) convertis automatiquement dans les liens et projets existants.
- **Limite connue** : un lien ne transporte que la configuration, pas le fichier 3D. Pour un modèle propre au joaillier (FBX), le client doit pouvoir le charger : prochaine étape = « Publier » (hébergement du modèle côté Netlify) pour obtenir un lien client court.

## Itération 4 : passe « chic » Domuse
- **Identité** : nom Domuse (logo au trait + wordmark Cormorant Garamond espacé), palette pierre / lilas gris / or sourd, mode sombre bleu-nuit (inspiré du compte Instagram de la joaillerie : fonds gris doux, pierres profondes). Polices embarquées via @fontsource (pas de requête externe).
- **Interface** : icônes au trait à la place des emojis, boutons fins, bouton principal encre, intitulés en petites capitales espacées, mode client sans barre : logo centré + trois actions.
- **Rendu** : éclairage par défaut = HDRI « Ville, plein soleil » (le studio s'affiche le temps du chargement) ; fond de scène gris pierre. Brossé : relief très léger pour éviter l'effet quadrillé en gros plan.

## Itération 5 — feuille repliable, liste des parties, vue éclatée

- **Feuille inférieure en accordéons exclusifs** (Parties / Matière / Teinte libre) : repliés par défaut, la vue 3D garde l'essentiel de l'écran ; animation `grid-template-rows` 0fr→1fr. Palettes en grille (plus de lignes tronquées).
- **Liste des parties à choix multiples** : lignes sobres (nom en serif, pastille matière, coche), outils « tout / aucune / similaires ».
- **Vue éclatée** (`src/core/explode.js`) : décalage radial par zone depuis l'origine du modèle, easeInOutCubic 900 ms avec léger décalage entre pièces, recul caméra automatique. Bouton global + bouton par partie. Les exports (GLB/AR/USDZ) et l'essayage remettent toujours la bague assemblée.
- **Éclatement** : le « haut » est déduit des pierres/sertissage ; le corps (rôle `body`) descend à l'opposé, le reste monte radialement.
- **Œil par partie** : masque/affiche une partie (réutilise `app.hidden`, annulable, conservé dans les liens de partage).
- **Correctif** : masquer/afficher une partie recalcule l'éclatement ; les positions d'origine sont désormais remesurées à l'état assemblé (avant, la bague restait éclatée). Test : `scripts/explode-regression.mjs`.
- **Mode Atelier retiré** (modes restants : Client / Joaillier). **Plein écran** masqué en mode client. **Thème clair/sombre** : palette ivoire-champagne-bronze (clair) et noir chaud-or (sombre), bouton lune/soleil dans la colonne d'outils, choix mémorisé, sinon réglage du système.
- Éclatement : les animations en cours ne sont plus annulées quand on masque/affiche une partie (cause probable du bug « reste éclaté » si on enchaîne vite).
- Bandeau d'aide et infos taille/diamètre retirés de la vue 3D (restent dans les exports).
- **Sélection pièce par pièce** : chaque partie à plusieurs pièces se déplie (chevron) en sous-lignes Pierre 1, 2… avec coche et œil. Bouton clair/sombre déplacé dans la barre du haut, à gauche du sélecteur Client / Joaillier.
- **Clic sur la bague** : 1er clic = toute la partie (ex. toutes les pierres latérales) ; clic suivant dans une partie déjà sélectionnée = ajoute/retire la pierre visée.

## Itération 6
- **Feature flags** (`src/config/features.js`) : rotation automatique, choix de l'angle de vue et gestion des lumières sont désactivés (boutons masqués, rotation coupée en Client et Joaillier) ; le code reste, il suffit de passer le flag à `true`.
- **Pastilles de couleur des pierres** : petites gemmes facettées (SVG généré, `src/materials/gemicon.js`) à la place des ronds — palette, en-têtes d'accordéon et liste des parties.
- **Rendu (PBR)** : MeshPhysicalMaterial (métal metalness 1, pierres en transmission/IOR/dispersion) + éclairage par image HDRI (IBL). Le HDRI « Ville, plein soleil » reçoit une balance des blancs chaude pour l'éclairage seulement (le fond reste fidèle) : l'or est moins verdâtre quand il reflète le ciel bleu.
- **Barre d'outils de vue** : explosion + plein écran en ligne en bas à droite ; libellé « Quitter le plein écran » supprimé (le bouton plein écran devient l'icône « réduire » en mode plein écran).
- **Clic 3D sur une pierre** : 1er clic = toute la partie ; 2e clic (partie entière sélectionnée) = isole la pierre touchée ; clics suivants = ajoute / retire la pierre touchée.

## Itération 7 — rendu physique des pierres et des métaux
- **Cause du rendu « plat » vs concurrent** : surtout l'éclairage (HDRI de ciel sans sources franches) et la transmission écran de three.js, qui ne sait pas faire de réflexions internes. Le HDRI n'était qu'en partie fautif.
- **Pierres = ray tracing intérieur** (`src/materials/gem.js`) : pour chaque pierre, une cube-map des normales de facettes et des distances est rendue une fois depuis son centre. Le shader (greffé sur MeshPhysicalMaterial) suit le rayon : réfraction (Snell), jusqu'à 6 rebonds internes (4 sur mobile), réflexion totale interne, Fresnel, dispersion sur 3 indices (R/G/B), absorption Beer–Lambert pour la couleur. Normales plates par facette.
- **Valeurs physiques** : IOR diamant 2,42 (borné à 2,6), rubis/saphir 1,77, émeraude 1,58… ; dispersion diamant 0,044 (écart B–R), amplifiée ×1,5 pour le rendu temps réel.
- **Éclairage** : HDRI « Ville » à balance chaude + softboxes procédurales (haut chaud, bandes latérales chaude/froide, fond) composées dans la scène PMREM → reflets doux et contrastés sur l'or, comme en studio.
- **Limites connues** : non testé sur iPhone réel (coût : 3 traces × rebonds par pixel de pierre) ; l'export GLB/AR utilise les matériaux de substitution (le shader n'est pas exportable) ; légère scintillation sur les diamants.

## Itération 8 — marque blanche (thèmes clients)
- **Un dossier par client** (`themes/<client>/theme.json` + logos + icônes). Le thème est choisi **au build** (`THEME=<client>`, défaut `domuse`) : un site Netlify par client, aucune identité d'un client dans le bundle d'un autre.
- Mise en œuvre : plugin Vite `config/vite-theme.js` (module virtuel `virtual:theme`, `<title>`/meta, manifest et icônes générés) ; `src/config/theme.js` injecte palettes clair/sombre + polices en variables CSS ; textes surchargeables par thème ; flags de fonctionnalités surchargeables.
- Charte Domuse : bordeaux `#31161f`, beige `#e5e1c8`, gris-bleu `#7d8e98`, papier Arena `#f0ece9` ; Inter seule (la typo des intitulés « Couleurs / Papiers » est écartée) ; clair = beige, sombre = bordeaux. Logos vectorisés (potrace) depuis les JPG fournis (`scripts/trace-logo.py`) : à remplacer par les fichiers d'origine si disponibles.
- Cormorant Garamond retiré ; `public/manifest.webmanifest` et `public/icons` remplacés par la génération depuis le thème. `themes/exemple` : thème de démonstration sans logo (repli texte).

## Itération 9 — zoom automatique sur la sélection
- Sélectionner une partie (clic 3D ou liste) cadre la caméra dessus ; pour des pierres, la vue passe de face (depuis l'extérieur de la bague) afin de bien voir couleur et facettes. Vider la sélection revient au cadrage d'ensemble en gardant l'angle courant. Pas de rezoom en changeant de pierre dans la même partie. Désactivable : flag `autoZoomSelect` (`src/config/features.js`, surchargeable par thème).

## Itération 10 — vue éclatée par étages
- L'éclatement se fait désormais **par étages le long de l'axe « haut »** : corps (descend légèrement) → sertissage (chatons, paniers, griffes) → pierres (en haut), avec un faible écart latéral pour séparer gauche/droite. Distances réduites (pas de plafond arbitraire à 55 % de la taille). La caméra se recentre sur l'ensemble éclaté.
- Mode client : le bouton d'explosion actif était invisible (fond transparent + texte de la couleur du fond) → états actifs et boutons plus contrastés (44 px).

## Itération 11 — modèle par défaut par client
- Clé `defaultModel` du `theme.json` : le fichier (dans `themes/<client>/`) est copié dans le build (`model/…`) et chargé au démarrage ; repli sur la bague de démonstration s'il manque. Domuse : `MAQUETTE_GEMV.fbx`. L'identifiant du modèle reste le nom du fichier, donc les liens de partage existants continuent d'appliquer leur configuration.
- Conséquence assumée : ce FBX est désormais accessible publiquement avec le site du client (avant, il n'était jamais embarqué dans le build).

## Itération 12 — « Nouveautés » et thème sombre par défaut
- **Fenêtre « Nouveautés »** (`src/config/changelog.js`) : une fois par visiteur à chaque nouvelle version (clé `rc:seenVersion`), montrant les entrées plus récentes que la dernière vue. Pas à la toute première visite (l'accueil suffit, la version est alors marquée vue), ni en mode client / lien client. Rouvrable via « Plus → Nouveautés ». **À chaque version : ajouter une entrée en tête de `CHANGELOG`.**
- **Sombre par défaut** : `defaultScheme: "dark"` dans le `theme.json` (appliqué avant le premier rendu, sans flash ; le choix mémorisé du visiteur reste prioritaire ; `"system"` pour suivre l'appareil). Couleur de barre / manifest alignées.

## Itération 13 — nuances d'or jaune, pierres nommées par espèce
- **Or jaune : 4 nuances** (intense, « Or jaune » = ancien identifiant `yellow` conservé, clair, champagne), du plus saturé au plus pâle (moins d'or pur, plus d'argent). Pas de titrage (carats) affiché : on garde le principe « une couleur, pas un alliage ».
- **Pierres nommées par la gemme qui a cette couleur** (Rubis, Émeraude, Saphir, Tanzanite, Péridot…). Les **identifiants ne changent pas** (liens de partage et projets existants intacts). Chaque pierre a son **indice de réfraction et sa dispersion B–G réels** (corindon 1,77 / 0,018 ; béryl 1,58 / 0,014 ; zircon 1,93 / 0,039 ; grenats 1,74–1,80 ; quartz 1,55 / 0,013 …), utilisés par le shader de gemme : moins de feu pour l'améthyste, beaucoup plus pour le zircon. Échelle de dispersion calée sur le diamant (0,044 ↔ 0,4).
- Anciens liens `tsavorite` redirigés vers « Tsavorite » (vert profond) au lieu de l'émeraude. Version 0.3.0 au journal des nouveautés.

## Itération 14 — contour de sélection, éclairage sans dominante gris-vert
- **Sélection 3D** : l'ancienne surbrillance (émissive) teintait la pierre et masquait sa couleur. Remplacée par un **contour** (coque inversée, épaisseur constante à l'écran, couleur d'accent du thème) tracé **autour de la silhouette** grâce à un masque stencil : visible même quand la pierre est sertie, et ne recouvre jamais la pièce → la couleur affichée est celle qu'on choisit. Survol = contour plus fin et translucide. Les contours sont retirés avant tout export (GLB, AR, photo). Le renderer active le stencil.
- **Éclairage** : le gris-vert venait du HDRI (ciel bleu + sol herbeux) reflété par l'or. Le HDRI « Ville » sert toujours de base (soleil, nuages, contrastes), mais sa couleur est neutralisée pour l'éclairage seulement : ciel désaturé (35 %) et réchauffé, sol remplacé par un fauve neutre ; softboxes de studio renforcées. Le fond 360° n'est pas modifié. Résultat vérifié sur or jaune, or rose et platine.

## Itération 15 — AR désactivée, finitions d'or réalistes
- **Flag `ar`** (`src/config/features.js`, défaut `false`) : le bouton « Réalité augmentée » est masqué pour tous les clients ; le code AR reste en place. Réactivable par client via `features: { "ar": true }` dans `theme.json`, ou ponctuellement par `?flags=ar` (test). Grilles d'actions adaptées (classe `has-ar`). Les tests ouvrent l'AR par `ui.openAR()`.
- **Finitions** recalées sur 4 photos de pièces réelles : **Brossé** = mat uniforme (rugosité 0,42) à grain très fin ; **Satiné** = reflet doux (0,26) + stries linéaires plus longues, discrètes ; **Martelé** = facettes planes polygonales inclinées au hasard, adoucies par un léger flou, rugosité 0,10 pour des facettes brillantes. Cartes de normales 1024 px ; `normalScale` propre à chaque finition (champ `normalScale` dans `FINISHES`). Vérifié par captures sur or jaune ; rendu du martelé dépendant des UV du modèle (étirements possibles sur les formes très courbes). Version 0.3.1.
- **Satiné, reprise** (retour : « pas de rayures, comme du satin », réf. photo fond blanc) : plus aucune carte de normales, juste une rugosité de 0,40 → reflets larges et doux, surface uniforme. On valide les finitions une par une (satiné ✔, brossé et martelé à revoir).
- **Brossé, reprise** (retour : grain dans le sens de la bague, pas perpendiculaire ; réf. alliance fond blanc) : la texture UV donnait un sens aléatoire selon le dépliage du modèle. Remplacée par un **grain procédural dans le shader**, orienté autour de l'axe du doigt (Z après normalisation, centre = centre du modèle, `setGrainFrame`) : stries fines le long de la circonférence, indépendantes des UV et de la vue éclatée. Rugosité 0,40, intensité 0,07 (`grain` dans `FINISHES`).
- **Martelé, reprise** (retour : martelage fin, facettes douces, or non réfléchissant comme du poli ; réf. bracelet) : la texture UV est remplacée par un **motif procédural 3D dans le shader** (cellules de Voronoï en espace objet, une facette légèrement inclinée par cellule, arêtes adoucies), taille de cellule 1,1 mm, cuvettes concaves (normale inclinée vers le centre de chaque coup, intensité 0,5), **rugosité 0,30** (plus de miroir). Indépendant des UV, suit la pièce en vue éclatée. Les anciennes cartes de normales (brossé/martelé UV) ne sont plus utilisées ; `getHammeredNormalMap` reste en code mort. Finitions validées : satiné, brossé, martelé.

## Itération 16 — le bouton de finition devient un curseur d'intensité
- Idée du client : le bouton actif sert de jauge. Affectation enrichie d'un champ optionnel `i` (0..1, ignoré pour Poli, borné, absent = valeur par défaut `i0` de la finition). **Satiné** : rugosité 0,14 → 0,56 (degré de satinage) ; **Brossé** : angle du grain 0 → 90° (de « le long de la bague » à « le long du doigt » ; seul le repère angulaire a une coupure, en bas de la bague, visible seulement aux angles élevés) ; **Martelé** : taille des cuvettes 0,5 → 2,2 mm.
- Interaction : toucher ou glisser sur le bouton actif règle `i` en direct (sans historique), relâcher enregistre une entrée d'annulation. Changer de finition remet l'intensité par défaut. Le bouton affiche un remplissage + un repère vertical (le texte reste lisible), rôle ARIA `slider`.
- Persistance : `i` dans les liens de partage et projets (5e élément du tableau compacté, en centièmes) ; anciens liens inchangés.
- Version 0.4.0 au journal (0.3.1 conservée).
- **Correctif satiné** : lors de l'ajout du curseur, le drapeau `satin` (carte de normales à stries) avait été remis par erreur dans `FINISHES` → traits visibles. Retiré ; test unitaire de non-régression (le satiné n'a aucune texture de relief).

## Itération 17 — introduction « écrin » (fusionnée ; le couvercle a ensuite été refait, voir itérations 21 et 22)
- **Idée du client** : à l'ouverture, la vue 3D montre l'écrin fermé ; au toucher, le couvercle se soulève **à la verticale** (pas de charnière), la bague sort de l'écrin, l'écrin disparaît et le configurateur apparaît.
- **Fidélité à la charte (Storez Studio, `Charte_Ecrins_V2.pdf`)** : base carrée avec épaulement et collier, couvercle à parois droites puis **pans coupés** et dessus plat plus sombre, suédine **bordeaux** (≈ #37020a / #54141d), intérieur en **suédine noire**, logo **DOMUSE marqué à chaud or (Kurtz 232)** sous le couvercle (option 2 de la charte : mot seul ; `intro.logo: "lockup"` pour l'option 1 « DOMUSE ATELIER PARIS »). Matériaux physiques à `sheen` + bump de grain pour l'effet suédine. Ces choix sont au thème (`theme.json` → `intro`), désactivé par défaut pour les autres clients.
- **Implémentation** : `src/intro/box.js` (géométrie procédurale proportionnelle à la bague, ~dizaine de maillages, aucun fichier 3D ajouté), `src/intro/intro.js` (machine d'états : attente → animation → fin ; ~3,5 s). La bague est descendue de 0,95 × sa taille et remonte ; pendant l'intro, interface masquée (`data-intro`), contrôles et rotation auto suspendus, ombre déplacée ; tout est restauré à la fin. Bouton « Passer », bouton « Touchez la boîte » (accessible au clavier), clic sur la boîte accepté seulement s'il n'y a pas de glissé.
- **Ignorée** si : `?nointro`, `prefers-reduced-motion`, ou en développement avec `?model=gemv` (tests) sauf `?intro=1`. `?introSlow=N` ralentit l'animation (captures).
- Particularité three ≥ r163 : `material.envMapIntensity` n'agit que si `material.envMap` est défini → l'environnement de la scène est passé explicitement aux matériaux de l'écrin.
- Test E2E ajouté. Non vérifié : rendu sur iPhone réel, perf du premier affichage (génération du logo en texture + 1 lumière directionnelle).
- **Retour client sur l'intro (v2)** : vue **de face, plongée légère (~17°)** ; le couvercle monte **à la verticale jusqu'à sortir complètement de l'écran** (distance calculée d'après le champ de la caméra) ; la bague sort et rejoint sa **pose exacte d'origine** ; la caméra glisse en continu (direction, distance, cible interpolées) de la vue de face vers la **vue d'accueil habituelle**, mémorisée avant l'intro → aucune coupure à la fin. L'ombre de contact et la lumière d'ambiance de l'intro s'estompent progressivement pour que la bague ne « saute » pas au retrait de l'écrin. Durée ≈ 3,9 s.
- **Correctif (retour iPhone)** : pendant l'intro, le panneau masqué laissait voir le fond de l'app, plus sombre que le fond 3D → cassure à la jonction. Le bas de la vue 3D se fond maintenant vers la couleur du fond (`.viewport::after`, actif seulement pendant l'intro, estompé en 0,8 s à la fin) ; les boutons du bas (annuler/rétablir/ouvrir) sont aussi masqués pendant l'intro.

## Itération 18 — épuration de l'essayage
- Retrait du bouton « changer de caméra » (⟲), du libellé « Recherche de la main… / Main détectée » et du curseur « Vision ». Le champ de vision reste à sa valeur calibrée (66°, ou celle déjà mémorisée).
- Nouveau curseur « Position » : déplace la bague le long du doigt (paramètre `along` de `computeRingPose`, 0,10–0,65, défaut 0,36, mémorisé).

## Itération 19 — qualité du suivi et sensation de 3D (essayage)
- **Points lissés avant la pose** : filtre One Euro sur les 21 points image et les 21 points « monde » (le bruit en profondeur faisait « tourner » la bague), puis filtre léger sur la pose. Réinitialisé quand la main est perdue ou le doigt/la position change.
- **Orientation** : le dessus de la bague suit à 85 % la normale mesurée du dos de la main (60 % avant), 15 % de rappel vers la caméra pour éviter les retournements.
- **Reflets liés au téléphone** : l'orientation du téléphone (capteurs, permission iOS demandée au toucher de « Activer la caméra ») tourne l'environnement des reflets en sens inverse, comme une pièce fixe. Repli silencieux sans capteur.
- Caméra 60 i/s demandés si possible ; seuils de présence/suivi MediaPipe 0,5 → 0,6.
- Non vérifié sur iPhone réel ; la photo de test fixe ne mesure ni la latence ni le tremblement.
- **Correctif (retour iPhone)** : avec 85 % de relief, la bague regardait sur le côté quand la main était inclinée. Retour à un dessus majoritairement tourné vers la caméra (relief 35 %), et direction du doigt mesurée sur MCP → DIP (plus longue, moins bruitée). Les reflets liés au téléphone gardent la sensation de 3D.

## Itération 20 — liens de partage toujours assemblés
- L'état éclaté n'a jamais fait partie du lien (le lien ne contient que modèle, matières, parties masquées, environnement), et un lien ouvert dans un nouvel onglet arrive assemblé (vérifié en test). Cas restant : coller le lien dans l'onglet déjà éclaté ne recharge pas la page (seul le `#` change) → la page se recharge maintenant sur tout changement de lien de partage.
- Ceinture et bretelles : à l'ouverture d'un lien de partage, la bague est rangée de force (`assembleNow`) après application de la configuration.

## Itération 21 — écrin laqué, bague cachée avant l'intro
- **Laque** (charte V3, photo de coffret bordeaux laqué) : l'extérieur de l'écrin passe de la suédine à une laque : `MeshPhysicalMaterial` avec vernis (`clearcoat` 1, rugosité 0,05) sur base bordeaux très sombre (#2a050c), reflets de l'environnement de la scène ; dessus plus mat (moins de reflet blanc). L'intérieur reste en suédine noire. 
- **Correctif aspect (reflets rayés, arêtes vives)** : cause géométrique, pas d'éclairage. Les cylindres à 4 segments avaient des normales lissées qui « gonflaient » les faces et striaient les reflets. Désormais : normales plates (`flat()`), base et couvercle en coques extrudées à angles arrondis et bord biseauté (`roundedShell`), couvercle droit (plus de pans coupés) avec dessous noir et logo. Intérieur de la base : le trou de l'extrusion était ignoré (coin tangent au contour + sens d'enroulement) → marge `ins` 0,09·S et trou inversé. Intérieur noir mat (env 0,03), dessus du couvercle moins réfléchissant.
- **Bague visible avant l'écrin** : le modèle est maintenant masqué dès son chargement quand l'intro doit jouer, et n'est affiché qu'une fois l'écrin posé autour (même image) ; filet de sécurité si l'intro est ignorée ou échoue.

## Itération 22 — pyramide plate, modèle hébergé pour les liens client, projets du joaillier (serveur et stockage Netlify : historique, remplacés par Firebase)
- **Couvercle** : retour à la pyramide plate (paroi droite arrondie, épaule inclinée, dessus plat sombre) en conservant la laque. Le couvercle est un habillage (`loft`) entre contours à coins arrondis ; épaule et dessus ont un reflet d'environnement réduit (sinon elles reflètent le plafond clair et virent au gris).
- **Liens de partage avec un modèle importé** : le fichier du joaillier est déposé sur le serveur à l'ouverture de la fenêtre « Partager » (inutile pour le modèle par défaut et la démo). Identifiant = SHA-256 tronqué (32 hex) du fichier : un même fichier n'est stocké qu'une fois. Le lien contient `u=<id>` ; à l'ouverture, le modèle est téléchargé puis la configuration appliquée, assemblé, interface client verrouillée. Repli : modèle par défaut + message si le modèle est introuvable ; dans la fenêtre de partage, message si l'envoi échoue.
- **Serveur** : fonction Netlify `netlify/functions/models.mjs` (route `/api/models/*`) + Netlify Blobs (store `models`, partagé entre production et previews). Logique dans `netlify/lib/models-api.mjs` (store injecté, testée en mémoire). Fichier compressé en gzip puis découpé en morceaux de 4 Mo (limite ~6 Mo par requête de fonction), 12 morceaux max (~48 Mo), 5 Mo par morceau.
- **Limites assumées** : pas d'authentification sur l'envoi (n'importe qui connaissant l'API peut déposer un fichier, dans les limites de taille) ; pas de suppression ni d'expiration. À durcir (jeton joaillier, quota) avant un usage ouvert. Le lien reste « secret par l'URL » (l'identifiant vient de l'empreinte du fichier).
- **Dev local** : plugin Vite `modelsApi` qui sert la même API avec un stockage en mémoire (dev et preview), ce qui permet de tester le parcours complet sans Netlify.
- **Projets du joaillier** : menu burger (en haut à gauche, masqué en mode client) → tiroir « Mes projets » : nom, Enregistrer / Mettre à jour / Enregistrer en nouveau, liste avec vignette, ouverture, suppression. Stockage local à l'appareil (IndexedDB : magasin léger `projects` + magasin `buffers` pour le fichier), donc un projet se rouvre sans réseau, avec fichier, configuration (matières, parties masquées, zones, variantes) et lumière. Pas de synchronisation entre appareils (piste : comptes joaillier).

## Itération 23 — migration vers Firebase (un seul fournisseur) (historique : Netlify a ensuite été retiré)
- **Décision** : tout chez Google Firebase (demande de Mehdi : un seul fournisseur) — Hosting (pages), Authentication (e-mail/mot de passe + Google), Cloud Storage (modèles), Firestore (projets). Guide d'installation : `docs/FIREBASE.md`.
- **Architecture** : couche `src/cloud/` avec une interface unique (`auth`, `models`, `projects`) et deux implémentations : `firebase.js` (si `theme.firebase` est renseigné dans `themes/<client>/theme.json` : un projet Firebase par client en marque blanche) et `local.js` (sans configuration : API `/api/models` + IndexedDB ; mode des tests et du développement, et de la production Netlify actuelle tant que Firebase n'est pas configuré). Le SDK Firebase est chargé à la demande.
- **Modèles** : un seul objet Cloud Storage par fichier (`models/<empreinte>`, gzip, métadonnées : nom, options), envoi direct depuis le navigateur (plus de découpage en morceaux ni de fonction). Le même objet sert au lien client et aux projets (dédoublonné par l'empreinte). Lecture publique par identifiant (pas de listing), création réservée aux joailliers connectés, 60 Mo max, sans écrasement. Cela ferme le trou « envoi sans authentification » de l'itération 22.
- **Projets** : `users/{uid}/projects/{id}` dans Firestore (nom, vignette, référence du modèle, configuration et options sérialisées en JSON car Firestore refuse les tableaux imbriqués) : synchronisés entre appareils. Compte requis pour enregistrer un projet et pour partager un modèle importé (le modèle par défaut et la démo restent partageables sans compte). Le lien client n'exige aucun compte.
- **Déploiement** : `firebase.json` (en-têtes équivalents à netlify.toml), workflow GitHub Actions (aperçu par PR, production sur `main`), scripts `deploy:rules` et `deploy:hosting`.
- **Non testé** : les émulateurs Firebase ne sont pas téléchargeables depuis l'environnement de développement (réseau restreint) et aucun projet Firebase n'existe encore. Vérifié : compilation, chargement réel du SDK avec une fausse configuration (formulaire de connexion, erreur réseau gérée) et le parcours complet en mode local. Les règles de sécurité et les échanges Storage/Firestore seront à valider au premier déploiement (CORS du bucket à configurer, voir le guide).
- **Netlify** : conservé tel quel jusqu'à la bascule (la production y tourne) ; à retirer ensuite (`netlify.toml`, `netlify/`, `@netlify/blobs`).

## Itération 24 — liens de partage courts (historique : Firebase n'est plus une option de build)
- **Lien court** : `https://site/#s=<12 caractères>` (≈ 50 caractères) au lieu de `#c=<configuration compressée>` (≈ 300 et plus). La configuration est déposée côté serveur, adressée par l'empreinte de son contenu (SHA-256 tronqué, 48 bits) ; l'ouverture du lien la récupère puis suit le même parcours qu'avant (modèle hébergé, configuration, assemblé, interface client verrouillée). Le QR code devient aussi plus simple.
- **Repli** : si le dépôt échoue (réseau, pas de compte en mode Firebase), le lien long `#c=` est généré comme avant ; les anciens liens longs continuent de fonctionner. Un lien court introuvable affiche un message et le modèle par défaut.
- **Serveur** : `/api/shares/:id` (GET/PUT, 16 Ko max, sans écrasement) ajouté à la fonction Netlify, renommée `netlify/functions/api.mjs` (routes `/api/models/*` et `/api/shares/*`) ; collection Firestore `shares/{id}` côté Firebase (lecture publique par identifiant, création par un joaillier connecté, pas de modification). Interface `cloud.shares` {put, get} pour les deux services.
- **Firebase en option de build** : la configuration n'est plus dans `theme.json` mais dans `themes/<client>/firebase.json`, injectée uniquement avec `vite build --mode firebase` (`npm run build:firebase`, `dev:firebase`, `deploy:all`). Un build normal (Netlify) reste en mode local, sans Firebase : la production Netlify n'est pas affectée tant que la bascule n'est pas faite. Le workflow GitHub utilise `build:firebase`.

## Effets 3D (rendu « qualité »)
- **Pipeline** (`src/core/fx.js`, `quality.js`) : la scène est rendue sans fond dans un tampon HDR prémultiplié (MSAA ×2 sur ordinateur) ; à l'arrêt, des images à décalage sous-pixel (Halton) sont **cumulées** (28 sur ordinateur, 10 sur iPhone) : arêtes fines lissées et **scintillement des pierres stabilisé**. Le fond est dessiné à part, sans tone mapping (raccord inchangé avec l'interface), puis l'image est encodée par-dessus. Le « rendu HQ » de la photo cumule 14 images (6 sur mobile).
- **Tone mapping AVANT le cumul** (leçon) : cumuler en HDR puis tone-mapper étalait les éclats de pierre (plusieurs centaines) sur les pixels voisins et gonflait la luminosité de toute la bague. Chaque image est maintenant tone-mappée (Neutral) avant la moyenne, comme le rendu direct : mesuré sur la même vue, luminosité moyenne 58,7 (direct) / 59,4 (1 image) / 60,0 (20 images cumulées).
- **iPhone** : rendu direct pendant le mouvement (comme avant) ; le cumul n'intervient qu'à l'arrêt ; ni profondeur de champ. `?fx=off` rétablit le rendu direct d'origine ; `?fx=mobile` simule le profil iPhone sur ordinateur.
- **Profondeur de champ** : propre (pas BokehPass, qui force l'alpha à 1) ; en gros plan uniquement, mise au point progressive, collecte pondérée pour éviter le halo autour de la bague.
- **Ombre de contact** (`contactShadow.js`) : vue du dessous, assombrissement selon la hauteur, double flou ; calculée une fois par changement de la bague (`Viewer.requestBake`, 300 ms après le dernier changement), pas à chaque image. Remplace le halo radial (conservé comme repli avant le premier calcul).
- **Pierres** : dispersion déjà propre à chaque pierre (valeurs réelles) ; ajout d'une **zonation / inclusions** (bruit 3D qui module l'absorption le long du rayon, 30 % sur les pierres de couleur, 0 sur le diamant).
- **Retirés après essai** : *reflet du sol* (miroir plan à 10 %, jugé inutile) ; *bloom* (il ajoutait ~10 % de luminosité et un voile : jugé trop lumineux) ; *micro-rayures de l'or poli* (lues comme des imperfections sur l'or de base) ; *sonde de reflets au centre de la bague* (dans le trou du doigt, elle voit l'intérieur de l'anneau : surfaces extérieures qui reflètent le mauvais environnement).
- **Non fait** : *occlusion ambiante entre les pièces* (SSAO/GTAO) : incompatible avec le rendu des pierres et le contour de sélection par stencil à un coût acceptable sur mobile ; l'ombre de contact couvre l'ancrage au sol.
- **À valider sur un vrai iPhone** : coût du cumul d'images avec le shader de pierres, mémoire des tampons HDR (plafonnés à 5 M de pixels sur ordinateur).

## Ateliers partagés et invitations
- **Modèle** : atelier partagé. L'atelier = l'espace du propriétaire (`users/{uid}/projects`, aucune migration) ; les invités y sont listés dans `workspaces/{owner}/members`. Un membre accède aux projets selon les droits que le propriétaire lui donne (voir « Droits des joailliers invités ») ; seul le propriétaire invite et retire. Chaque joaillier a son propre atelier et peut en rejoindre d'autres (sélecteur).

L'e-mail saisi n'est qu'un repère pour le propriétaire (et le destinataire du bouton « e-mail ») : **qui détient le lien peut le consommer**, d'où l'usage unique et l'avertissement « à n'envoyer qu'à la personne invitée ».

Les tests ont révélé une faille de ma première version (un lien pouvait servir à plusieurs personnes car l'adhésion ne consommait pas le jeton) : corrigée.
- **Propriété** : tout ce qu'un invité enregistre appartient à l'atelier du propriétaire ; le dialogue d'invitation et celui d'acceptation le disent.
- **Inscription libre conservée** (choix) : n'importe qui peut toujours créer un compte et son propre atelier (risque de coût/abus de Cloud Storage décrit dans la revue d'audit ; à traiter séparément : liste d'invitation globale, vérification d'e-mail ou App Check, alerte de budget).
- **Émulateurs** : `?emulator` (développement uniquement) branche l'app sur Auth/Firestore/Storage locaux (`demo-jewel3d`).

Le hook saute les vérifications si aucun fichier de l'application n'a changé ; `SKIP_VERIFY=1 git push` l'ignore ponctuellement.

## Liens clients suivis (backoffice)
- **Pourquoi un nouveau modèle** : les liens `#s=` étaient adressés par le contenu (deux envois identiques = même lien) et sans propriétaire : impossible de les attribuer, suivre ou désactiver. Un lien suivi = un identifiant aléatoire de 80 bits (`#l=`), un propriétaire, un état (actif / désactivé / expiration). Les anciens liens restent valables, sans suivi.
- **Deux documents** : `links/{id}` public (le client le lit sans compte) ne contient rien de privé ; le nom donné au lien, la note et la vignette sont dans `users/{uid}/links/{id}` (lisible du seul joaillier). `enabled` / `expires` sont dupliqués dans la fiche privée (écrits ensemble, en une écriture groupée).
- **Mesure côté client, sans Cloud Function** : le client reçoit un compte **anonyme** (la règle exige un compte pour limiter l'écriture) et écrit/met à jour sa ligne `views` toutes les 10 s avec le temps visible, les actions et un type d'appareil à gros grain. Les règles bornent tout (compteurs qui ne reculent pas, temps ≤ temps écoulé + 5 s, longueurs, valeurs d'appareil) mais **un client déterminé peut falsifier ses propres chiffres** : ce sont des indicateurs de suivi, pas une preuve.
- **Agrégation côté joaillier** : une requête de groupe `views where owner == uid` (index à déployer) puis agrégats en mémoire (`linkStats.js`, testé). Suffisant pour quelques centaines de liens ; au-delà il faudrait des compteurs maintenus par une Cloud Function.
- **Durcissement lié** : `signedIn()` exclut désormais les comptes anonymes partout (projets, liens courts, invitations, adhésions) et la règle Storage refuse le dépôt de modèles aux anonymes. Règles testées sur l'émulateur.
- **Information et droits du client** (`privacy.js`) : bandeau « Mesure d'audience anonyme de ce lien. En savoir plus » visible dès l'ouverture (écrin compris) ; page de détail (données enregistrées / non enregistrées, finalité, hébergement Google, conservation 13 mois, droits via le joaillier) ; **refus à tout moment** (`optout.js`, mémorisé sur l'appareil, la mesure s'arrête immédiatement et ne reprend pas aux visites suivantes). **Conservation** : chaque consultation porte `expireAt` (≤ 400 j, imposé par les règles) et une politique TTL Firestore la supprime ; sans cette politique (à activer une fois) la mention serait fausse. Le texte juridique est une proposition : à faire valider (RGPD / ePrivacy ; le joaillier est responsable du traitement, la plateforme sous-traitant). Aucune IP, localisation ou identité ; le joaillier connecté qui teste son lien n'est pas compté.
- **Pas fait** : notifications (« votre client vient d'ouvrir le lien »), export CSV, suivi des anciens liens `#s=`.

## Classification des pièces : pierre centrale à maillage dense
- **Cas réel** (lien `#s=ad51bb0c4d4b`, FBX de 74 pièces) : la pierre centrale (1 204 triangles, UV présents, matériau générique « Matériau_2 ») était classée **métal** — l'ancienne règle géométrique n'attrapait que les pièces « < 1 000 triangles ET sans UV » — puis rangée avec les paniers latéraux. Ses griffes (3 400 triangles pour 3 mm) tombaient dans « Chaton » au lieu de « Griffes », et un pavé de 58 petites pierres décalait le barycentre : la « pierre centrale » affichée était une pierre latérale.
- **Règles** (`zones.js`, `analysis.js`) : (1) un **solide convexe** de taille ≥ 2 % du modèle est une pierre (test orientation-indépendant sur un échantillon de faces ; les pierres sont à ≈ 0, les métaux d'une vraie bague à ≥ 1,8 %, mesuré sur 2 modèles) ; les mots-clés de noms priment toujours ; (2) **pierre centrale = la nettement plus grosse** (volume ≥ 1,8 × la suivante), sinon repli sur le barycentre ; (3) **griffe** = petite pièce (< 16 % du modèle) même très maillée ; (4) `detectZones` respecte le `kind` décidé à l'import (il re-classait par les noms seuls).
- **Vérifié** sur le fichier réel : zones « Pierre centrale 1 / Pierres latérales 58 / Chaton central 1 / Griffes 9 / Corps 5 » ; le modèle de référence du thème donne des zones **identiques** avant/après ; l'ancien lien s'ouvre avec la pierre centrale en diamant (la matière « métal » enregistrée pour cette pièce est ignorée car la pièce est maintenant une pierre).
- **Limite** : un métal plein et convexe de grande taille (disque, barre) serait pris pour une pierre ; la correction manuelle (changer le type d'une zone) reste disponible. 14 tests unitaires sur géométries synthétiques (`classification.test.js`), sans fichier privé.

## Droits des joailliers invités
- **Besoin** : donner accès aux projets **un par un** et choisir, personne par personne, les fonctionnalités de l'atelier.
- **Modèle** (appliqué par les règles, pas seulement par l'interface) : `workspaces/{owner}/members/{uid}` porte `projects` (`all` | `selected`) et `perms` (`save`, `delete`, `createLinks`, `viewLinks`) ; chaque projet porte `sharedWith` (liste d'uid). Un invité voit un projet s'il lui est accordé, ou s'il est en mode `all` et que le projet n'est pas privé. Valeurs par défaut : voir tout (non privé), créer et modifier oui, le reste non. Pures et testées dans `src/cloud/rights.js`.
- **Liens clients d'atelier** : le lien créé par un invité autorisé appartient à l'atelier (`owner`), avec son auteur (`by`). Sans `viewLinks`, l'invité ne voit que ses liens, sans statistiques (les consultations ne portent pas l'auteur du lien : le seul moyen de les ouvrir sans ce droit est le lien lui-même).
- **Compatibilité** : les anciens invités gardent leur accès mais perdent la suppression (le droit n'existait pas : défaut prudent). Un invité qui crée un projet y a accès (`sharedWith = [lui]`) même en mode sélection.
- **Pas fait** : droits par rôle (modèles de droits réutilisables), journal des accès accordés, droit « inviter ».

## Sélecteur de pierres : l'Atlas chromatique des gemmes
- **Source** : le PDF « Atlas chromatique des gemmes » (7 familles : rouge/pourpre/rose, bleu/cyan/aigue-marine, vert/olive/jade, jaune/doré/orange, violet/mauve/indigo, incolore/brun/noir, polychromes). Le sélecteur reprend ces familles (titres) et leurs pierres : 52 entrées (23 avant), dont les anciens identifiants, **inchangés** (projets et liens existants intacts). `citrine`, `turquoise` et `lapis` deviennent de vrais identifiants (ils pointaient sur d'autres pierres) ; `topaz` ancien → topaze bleue.
- **Données par pierre** (`library.js`) : espèce, dureté de Mohs, indice et dispersion réels, un repère visuel. Fiche affichée sous le nom de la pierre choisie : espèce · dureté · indice, **avertissement sous dureté 7** (« craint les rayures en bague de tous les jours »), et pastilles des **autres variétés de la même espèce** (le « caméléon » de l'atlas : corindon = rubis, saphirs de toutes couleurs, padparadscha…). Recherche par nom, espèce ou famille (sans accents), sans reconstruire la feuille.
- **Pierres opaques à motif** (`gem.js`) : lapis (veines de calcite, paillettes de pyrite), turquoise (matrice), jade, malachite (bandes), œil de tigre (fibres + reflet), cornaline, charoïte, sugilite, rhodochrosite, opale noble (feux selon l'angle), labradorite (éclairs bleu/or), pierre de lune (adularescence). Motifs **procéduraux en espace objet** (bruit 3D, mêmes principes que le martelé des métaux) : pas de texture, indépendant des UV, léger. Vernis adouci : la table plane d'une pierre opaque miroite l'éclairage et écrasait le motif.
- **Effets** : **alexandrite** = deux teintes d'atténuation mélangées selon la *chaleur de l'éclairage* (`warm` par environnement : vert-bleu de jour, rouge-violet au coucher du soleil, valeurs intermédiaires pour l'atelier) ; **ametrine** = deux moitiés (améthyste / citrine) dans la même pierre ; **hématite** = éclat métallique.
- **Non fait** : chatoyance « œil de chat » en vraie anisotropie, astérisme (saphir étoilé), pierres bicolores par pièce (tourmaline pastèque), changement de couleur lié à une source lumineuse réelle plutôt qu'à l'environnement. Les vignettes 3D de pierres (jamais affichées) sont supprimées du démarrage : 52 rendus coûteraient pour rien.
- **À valider sur iPhone** : coût du bruit 3D dans le shader des pierres opaques (fbm à 4 octaves, quelques appels par pixel).
- **Cabochons (retour : comparaison avec une photo de rhodochrosite réelle)** : une pierre opaque est presque toujours un cabochon poli, pas une pierre à facettes. Le modèle de la bague reste facetté, donc la normale de surface des pierres opaques est **bombée** (direction depuis le centre de la pierre, mélange 85 %) : reflets doux et continus, la silhouette ne change pas. Vernis net (`clearcoat` 0,5–0,6, rugosité 0,07). **Translucidité** (`sss`) : une part de la couleur est ajoutée en émission, plus forte vers les bords, pour que les ombres ne virent pas au noir (rhodochrosite, jade, cornaline, turquoise, pierre de lune…). **Rhodochrosite** : plus de bandes concentriques ; fond rose-corail, nuages profonds, voiles laiteux étirés et fines inclusions claires.
- **Œil de tigre (retour : photos de pierres réelles)** : fini le zèbre régulier. Larges bandes **irrégulières** (largeur variable, déformées), brun sombre / ambre / or, zones olive-noir, **fibres très fines** (bruit étiré le long des fibres), et surtout la **chatoyance** : une ligne lumineuse dorée, perpendiculaire aux fibres, là où la surface leur est tangente ; elle **glisse quand on tourne la pierre ou la caméra**, comme sur une vraie pierre.
- **Cartes de brillance, de spéculaire, de relief et d'occlusion (suggestion : « Specular / AO / Glossiness map »)** : des cartes image se plaquent par UV, or les fichiers de bijouterie (CAO) n'ont pas d'UV fiables. Mais **le motif de couleur est généré par le programme : on sait où est chaque veine, bande ou paillette**, donc les autres cartes s'en déduisent. Retour décisif : *les effets de lumière doivent correspondre aux caractéristiques de la texture*. Première version = trois fonctions qui recalculaient des motifs voisins (et la position des paillettes de pyrite avait dérivé entre la couleur et le reflet). Maintenant **une seule source de vérité** (`gemPatEval()` dans `gem.js`) calcule, une fois par pixel et dans l'espace de la pierre, la couleur, la rugosité (*glossiness map*), le spéculaire (*specular map*), la hauteur (relief) et les masques d'effets ; le reflet dépendant de l'angle (`gemPatGlow`) lit les mêmes masques. Exemples : veines de calcite du lapis plus mates et en creux, paillettes de pyrite brillantes, en relief et étincelantes **exactement** là où la couleur les place ; matrice de la turquoise plus dure donc brillante ; bandes de malachite inégalement polies ; fibres de l'œil de tigre = éclat soyeux ; voiles laiteux de la rhodochrosite plus mats.
- **Relief** : bump mapping par dérivées d'écran de la hauteur (sans UV). Limité aux motifs **lisses** (veines, bandes) et faible (0,2) : sur un grain fin les dérivées d'écran (blocs de 2×2 pixels) donnent des artefacts visibles, essayé puis réduit.
- **Occlusion ambiante** : `gemAO()` assombrit le bord d'une pierre sertie (diffus et reflet d'environnement indirect, jamais la lumière directe), force 0,5.
- **Non fait** : AO cuite par sommet sur les métaux (lancer de rayons sur toute la bague : plusieurs secondes au chargement et pesant sur mobile) ; micro-variations de rugosité sur l'or poli (rejetées : lues comme des imperfections) ; cartes image importées par pierre.

## Performance de chargement (rapport Lighthouse : LCP 4,5 s, TBT 270 ms, charge de 4,7 Mo)
- **Mesure** (build de production, page de connexion) : avant, 2 336 Ko de JavaScript décompressé **avant même le formulaire** (three.js 980 Ko, MediaPipe 150 Ko, Firestore 480 Ko, toute l'interface). Maintenant **302 Ko** (−87 %).
- **Point d'entrée léger** (`main.js`) : lit le lien, applique la porte d'entrée, affiche la connexion. L'application (`appMain.js` : three.js, interface, importeur) n'est chargée qu'ensuite ; l'essayage (`tryon`, MediaPipe) à la première ouverture. **Préchargement malin** : lien client → code chargé en parallèle de la lecture du lien ; connexion → code chargé au premier geste (clic, touche) sur le formulaire, de sorte que l'appli s'ouvre aussitôt après la connexion (pas `focusin` : la page donne d'elle-même le focus au champ e-mail). Le modèle par défaut est téléchargé dès que l'on sait qu'il servira, en parallèle de three.js.
- **Connexion = authentification seule** (`firebase-auth.js`, instance partagée avec `firebase.js`) : Firestore et Storage (≈ 480 Ko) ne se chargent qu'après la connexion (en arrière-plan) ou pour un lien client.
- **Pièges rencontrés** : (1) le chunk manuel « mediapipe » emportait l'assistant d'import dynamique de Vite : il se chargeait donc partout ; supprimé, MediaPipe est rangé avec l'essayage. (2) `window.__rc = { THREE }` empêchait de retirer le code three.js inutilisé : THREE n'est plus exposé qu'en développement (−25 Ko gzip). 
- **Écran d'attente de marque** intégré au HTML (logo + barre) : premier affichage immédiat au lieu d'une page vide pendant le chargement du JavaScript (`splash()` dans `config/vite-theme.js`).
- **Tâches longues** : les billes de métaux/finitions (second contexte WebGL, plusieurs centaines de ms) ne sont plus calculées pour un client (pas de palette) et, pour le joaillier, sont différées au repos du navigateur. **Animations composées** : barres de progression et halo de l'écrin animés en `transform` / `opacity` (plus de `width` ni de `box-shadow`).
- **Non fait, à décider** : le modèle par défaut pèse **4,9 Mo même compressé (brotli)** : c'est l'essentiel de la charge d'un lien client. Le FBX est non indexé et en flottants 32 bits ; une conversion en GLB quantifié (meshopt) le diviserait sans doute par 3 à 5, au prix d'un outil d'encodage à ajouter au projet et d'une revérification de la classification des pièces. Autres pistes : HDRI de 1,4 Mo (résolution réduite), écrin affiché avant l'arrivée du modèle.

## Itération 27 — Atelier d'or (texture de métal sur mesure)
- Besoin : le joaillier n'est pas satisfait du rendu de l'or → outil pour fabriquer sa propre texture, avec tous les réglages PBR et l'éclairage ambiant, enregistrée sous un nom.
- Nouveau type d'affectation de métal `{ m: 'lab', l: {...} }` (`src/materials/lab.js`) : couleur F0, gain de luminosité, métallicité, rugosité, IOR, intensité/couleur spéculaire, vernis (clearcoat + rugosité), anisotropie (force, direction), irisation (intensité, IOR, épaisseur), voile (sheen), lueur (emissive), texture lisse/satiné/brossé/martelé + intensité + relief. Valeurs bornées/nettoyées par `sanitizeLab` (liens et projets viennent de l'extérieur).
- La texture voyage DANS l'affectation : liens de partage (forme compacte : seules les valeurs ≠ défaut, regroupées par contenu) et projets l'emportent sans serveur ni règle Firestore. La bibliothèque de textures nommées est stockée dans l'atelier du joaillier administrateur : Firestore `users/{propriétaire}/labs/{id}` (nom, réglages compacts, éclairage, auteur), lisible par tous les joailliers de l'atelier (`canWork`), écriture : propriétaire ou membre avec droit `save`, suppression : propriétaire ou droit `delete`. Changer d'atelier recharge la liste. Sans compte (mode local) ou hors ligne : copie `localStorage rc:labs`. Règles à déployer (`npm run deploy:rules`) ; test `tests/rules/labs.rules.test.js` (émulateur, non exécutable dans le bac à sable).
- Éclairage ambiant : intensité de l'environnement (`scene.environmentIntensity`) et exposition, enregistrés avec la texture (case à cocher), puis portés par le lien (`i: [n, x]`, seulement s'ils ont changé) et par la config du projet (`light`). Chargement d'un modèle sans `light` → éclairage remis à 1/1.
- Performance : un curseur ne recompile pas le shader ; `needsUpdate` seulement quand une fonction s'active/désactive (clearcoat, anisotropie, irisation, sheen, emissive, normalMap).
- Interface : feuille « Atelier d'or » (remplace la feuille matière, la bague reste visible), ouverte depuis la tuile ✦ de la palette des métaux ou le menu burger ; réglage en direct sur les métaux sélectionnés (sinon tous). Une seule étape d'historique par séance.

## Itération 31 — Gemmes de couleur plus fidèles (pierre jaune)
- Constat : sur la pierre jaune (taille émeraude), l'app rendait un olive sombre et saturé (10 % des pixels les plus sombres à V≈0,36, S≈0,88) là où la vraie pierre reste lumineuse et translucide (V≈0,79, S≈0,57), avec des plages rose/grises et un grain brun.
